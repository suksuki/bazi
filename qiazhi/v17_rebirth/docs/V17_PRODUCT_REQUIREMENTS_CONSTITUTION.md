# V17 产品需求宪法

日期：2026-04-25  
状态：Living Document，后续产品、架构、UI、Prompt、插件和学习系统设计均应围绕本文更新。

## 1. 北极星定位

V17 不是一个普通的八字排盘页面，也不是一个把传统术语包装成聊天机器人的工具。

V17 的核心定位是：

1. 一个可以自我学习和进化的八字测算系统。
2. 一个深度结合 AI 技术的八字推理系统。
3. 一个面向职业和业余命理师的可审计推理平台，让他们获得更多八字推理信息、逻辑支撑，并能深度参与反馈、验证和修正系统。

一句话定义：

> V17 是一个以命理师为重要共建者、以证据和反馈为核心、由 AI 辅助解释和进化的八字推理系统。

## 2. 核心用户

### 2.1 职业命理师

他们需要：

- 快速看到命盘结构、用忌、格局、运势与风险的推理证据。
- 看到系统为什么这样判断，而不是只看到一句断语。
- 能对格局、用神、关系、风险、断语进行确认、否定、补充和校正。
- 把系统作为助理、校验器、资料整理器，而不是被系统替代。

### 2.2 业余命理学习者

他们需要：

- 读得懂的结论。
- 可逐层展开的推理链。
- 能从系统输出中学习命理逻辑，而不是只得到玄学化结果。

### 2.3 普通测算用户

他们需要：

- 简洁、可信、不过度恐吓的断语。
- 手机端顺畅的输入和结果阅读体验。
- 不被大量工程调试信息淹没。

### 2.4 系统管理员与研究者

他们需要：

- 插件、参数、Prompt、LLM、数据库与学习记录的可观测性。
- 明确的权限边界。
- 能复盘每一次判断的来源和演化。

## 3. 不可偏离的设计原则

### 3.1 证据优先

任何强断语都必须能追溯到结构化证据：

- 四柱、运柱、流年。
- 十神能量与来源。
- 干支关系、合冲刑害、三合三会。
- 格局候选、用忌证据、风险证据。
- Prompt 与 LLM 输出中的引用依据。

禁止把候选格局、弱证据、LLM 猜测直接写成定论。

### 3.2 AI 是推理协作者，不是黑箱神谕

AI 的职责是：

- 压缩和组织复杂证据。
- 生成更易读的断语。
- 帮助命理师发现冲突、遗漏和可疑点。
- 根据反馈参与系统进化。

AI 不应：

- 绕过底层物理层直接下结论。
- 把没有 evidence 的内容包装成权威判断。
- 用长篇玄学文本掩盖证据不足。

### 3.3 命理师反馈必须是一等公民

系统必须长期支持命理师参与：

- 对格局候选给出确认或否定。
- 对用神、忌神、风险点给出修正。
- 对 LLM 断语给出“准确、偏差、过度、遗漏”的标注。
- 对真实案例做验证。

反馈不只是评论文本，而应绑定到：

- `chart_snapshot`
- `evidence_key`
- `pattern_candidate`
- `claim_id`
- `verdict`
- `reason`

### 3.4 自我学习必须受治理

V17 可以学习，但不能失控自动改写核心规则。

学习系统应优先调整：

- 参数权重。
- 证据门槛。
- 候选升降级策略。
- Prompt 表达策略。
- 案例排序和置信度。

核心命理定义、插件协议、物理层规则必须经过测试、审计和版本记录。

### 3.5 多语言、多终端、权限控制是基础维度

任何新功能都必须同时考虑：

- 多语言：中文、英文、韩文输出一致，不允许新增中文孤岛。
- 多终端：桌面端信息密度可高，手机端必须流程化和分层。
- 权限：`admin / manager / user` 的能力边界必须明确。

这三项不是后期补丁，而是架构输入。

## 4. 产品形态原则

### 4.1 桌面端

桌面端面向深度分析和命理师工作台：

- 可以展示较高信息密度。
- 应支持证据面板、调试视图、Prompt 追踪、插件结果。
- 适合横向比较、复盘和审计。

### 4.2 手机端

手机端必须流程优先：

1. 选择功能。
2. 输入信息。
3. 得到核心断语。
4. 分层查看命盘、用神、关系、风险。
5. 需要时再进入深度解释。

手机端不应把桌面调试面板直接堆叠下来。

### 4.3 断语风格

默认断语应短、准、克制：

- 先给判断。
- 再给要点。
- 最后给一条可执行提醒。

深度解释、证据展开、Prompt 审计应放到专门入口。

## 5. 架构原则

### 5.1 分层结构

系统应坚持：

1. 物理层：干支、十神、关系、运流等可计算事实。
2. 证据层：格局、用忌、风险、主题等候选证据。
3. 裁决层：处理冲突、置信度、优先级和候选升降级。
4. 叙事层：面向用户输出短断语、解释和多语言文本。
5. 反馈层：收集命理师和用户反馈。
6. 学习层：在治理下调整参数、门槛和表达策略。

### 5.2 Evidence / Claim / Feedback 三件套

后续新增功能应优先回答：

- Evidence：这个判断的证据是什么？
- Claim：系统最终主张是什么，置信度如何？
- Feedback：命理师如何反馈这条主张？

没有这三件套的新功能，默认不视为完整功能。

### 5.3 插件不是孤岛

每个插件必须：

- 声明自己的命理语义。
- 输出结构化 `V17Fact` 或等价 evidence。
- 标注 `observe_only`、`claim_type`、`candidate_status` 等语义边界。
- 可被测试、审计、反馈和调参。

## 6. 数据与治理原则

### 6.1 真实案例是系统进化的燃料

系统的长期优势来自：

- 真实命盘。
- 命理师反馈。
- 用户验证。
- 自动化回归。
- Synthetic Lab 和 Practitioner Benchmark 双轨校准。

### 6.2 数据必须可回放

每次重要判断都应尽量保留：

- 输入命盘。
- 当时参数。
- 插件 evidence。
- LLM prompt 与输出。
- 用户语言与终端上下文。
- 反馈记录。

### 6.3 学习结果必须可撤销

任何自动学习或参数调整都应具备：

- 来源记录。
- 版本记录。
- 回滚路径。
- 测试门禁。

## 7. 新功能准入清单

每个新功能进入实现前，应检查：

- 是否服务于“自学习 + AI 推理 + 命理师共建”的北极星？
- 是否有 evidence，而不只是 UI 文案？
- 是否支持命理师反馈或未来可接入反馈？
- 是否兼容中文、英文、韩文？
- 是否兼容桌面和手机？
- 是否考虑 `admin / manager / user` 权限？
- 是否有测试或验收用例？
- 是否不会把候选判断伪装成定论？

## 8. 近期优先级

当前阶段最重要的方向：

1. 建立命理师反馈闭环。
2. 把古典格局、用神、风险等判断统一到 evidence 层。
3. 让 LLM 输出从“长篇解释”转向“短断语 + 可展开证据”。
4. 优化手机端流程化体验。
5. 建立真实案例基准集与自动化回归。

## 9. 更新规则

本文档可以更新，但更新必须遵守：

- 不轻易改动北极星定位。
- 如果新增用户类型，需要说明其与命理师共建目标是否冲突。
- 如果新增架构原则，需要说明它如何支持 evidence、claim、feedback 和 learning。
- 如果调整 UI 原则，需要同时说明桌面端和手机端影响。
- 重大变更应在文末变更记录中追加日期和原因。
